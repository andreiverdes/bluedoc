# Replies

Rules for what `serve.py wait` prints. Read once per session.

- **Answers** (picks, ticks, comments): act on each pick; no pick means undecided, so ask. An item comment is an instruction about that item and can override its pick. A `multi` item's pick is a list: `→ **Lyon**, **Porto**`. **Other** is the reader's own answer (`→ **Other**: <text>`, JSON `choice: "custom"` with the words in `custom`; with several answers one more in the list): treat it as their decision, and if it doesn't say what to do, ask with `--reply`. Other on a brief's `framework` or `theme` is a request: add it as an option (an id the build knows, with its `md`) in the next rev and leave the item unpicked, so the reader picks it there. A comment written in an answer's field names that answer (`> On **90 days**: why not this one?`, JSON `comments: [{about: "d90", md}]`): it asks about that answer and picks nothing; answer it with `--reply … --on d90`. A comment without `On` is about the pick, or (`note`) the whole question. On a review with `meta.review`, do what its send key says (`types/review.md`): `post` replies carry `Post as:` per PR and the header's `review events`: post each PR with its own event. A review's answers carry picks and ticks only: its comments on findings and **Tell me more** come with the change request, each finding under `## Decisions` with its pick as context and its comments quoted.
- **Answer comments in their conversation**: each comment ends with `→ <key> · <id>` (an item's `→ item:<checklist>/<item>`, no id); the commands under `## Answering` at the end take them: `build.py patch <doc> <key> --reply "…" --resolves <id> --no-bump` (`ann:<id>` for a pin or general comment; drop `--resolves` without an id). On a question, add `--on <option id>` when the reply answers a comment about one answer (`On **90 days**`); without it the reply is about the whole question. Keep it short and direct. Change the item itself only when the answer changes the question or its options. One reply per call.
- **Attached files**: a comment may list `Files:` with full paths (copies in `~/.bluedoc/attachments/`). Read each one before you act on or answer that comment; it is part of the instruction.
- **Tell me more** (`item:… → **Tell me more**`): in the next rev, answer its comment with `--reply`, sharpen that item's options and their `md` explanations (or add one), and keep it unpicked; `--resolves` doesn't apply.
- **Change requests**: each annotation names a `key`; pass it to `patch` as is. The annotator writes `doc` (general notes: apply across the doc), `header`, `tldr`, `status`, `section:`, `heading:`, `lead:`, `block:`, `item:`, `row:`, `card:`, `para:`, `step:`, `file:`, `media:`, `compare:`, `node:`, `comment:` and `line:` keys, and on design, presentation and website pages `artboard:`, `el:`, `frame:`, `link:`, `layout:` and `board:` (a Region or drawing on the board itself: its `Where:` line gives its box in board px and its part on each screen or page under it, in that frame's px; change those by their `artboard:` or `el:` keys), and on storelisting pages `field:`, `brand:`, `section:<platform>/<row>` and `variant:`; their grammar is the table under `## Annotations` in `references/schema.md`. A `line:` key patches the review comment covering that line; with none, change the code or patch the finding. An `el:` key: `patch` prints the screen file and selector (on a website's live page: the URL, selector and source hints); edit there. Board drafts (`link:`, `layout:`, and `el:` element drafts: a reader's text edit or deletion in Edit, applied with `patch el:… --set 'text="…"'` or `--delete`; on a live page edit the source the `Source:` line names, then run its `--change` command) and a listing's drafts (`## Text edits`, `## Uploaded shots`, `## Style picks`, `## Brand drafts`, `## Accepted MT`) come with a ready command: run it. One you can't or shouldn't do: say so in `changes` or ask, never skip it silently.
- **A note with the send**: Request changes, Approve and Send answers may carry the reader's note, the paragraph under the Markdown's title (JSON `note` with `noteFiles` on a change request or an approval, `message` with `messageFiles` on answers). It applies to the whole reply: read it first.
- **Approval** (plans, designs, websites): implement exactly the approved rev, as `types/plan.md` and `types/design.md` say. Presentations and store listings aren't approved: their picks come with change requests.
- **Plan mode** (Claude Code): ExitPlanMode is denied with a message naming the plan doc and its URL. Follow it: `wait` in the background, `patch` that doc on a change request, call ExitPlanMode again after the approval.
- **Revise** per target: `build.py patch <doc> <key> --set field=value --change "what changed and why"` (nested `--set a/b/c=v`; `--json`, `--append`, `--delete` for more). It validates, bumps `meta.rev`, replaces `changes`, records history and prints the `?diff=` link to send. Several patches for one reply: bump on the first, `--no-bump` on the rest. Once you have sent the reader a rev's URL, never edit it in place. A built doc is patch-only: bluedoc's hook refuses edit and write tools on it.
- **A shared doc** (`build.py patch` then prints its share line: the link's rev and the hour's count, a queued update, or a pause): GitHub allows about 100 gist updates an hour per account and bluedoc sends at most 90, one a minute per doc. Keep the link current with one `serve.py share <doc>` once the round's patches are in, never after each patch or in a loop. `queued` is done: it goes out by itself with the doc as it is then, this round's later patches included. `paused`: tell the user; only they resume (**Resume updates** in the Share sheet, or `serve.py share --resume`). A new rev never updates the link by itself.
- **Resolve**: pass each addressed comment's id with `--resolves ID`. Never list one you didn't do.
- Record the reader's picks as `choice` and finished, verified work as done (steps `status: "done"`, checklist items `done: true`), with optional `evidence`: what you ran and saw, a screenshot, a link to a log or review. Send the `?diff=` link, then `wait` again.
- **Evidence is pinned**: record it with `build.py patch` right after the check runs, so it carries the commit (and uncommitted changes) it checked; `--paths` names what the check covers. After changing code a check covers, re-run it and re-record with `build.py patch <doc> <key> --pin`. Stale evidence (code changed since) shows on the page, doesn't count as done, and comes back under `## Stale evidence` with those commands.
- Commit `<name>.bluedoc.history.json` with the JSON.
- **Archive** is the reader's (the page's ⋯ menu, a home card's): never archive a doc yourself. An archived doc still takes replies; a new rev brings it back to the home page.
