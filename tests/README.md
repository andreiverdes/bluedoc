# Tests

Run `python3 -m unittest discover -s tests` from the repo root (Python 3.9+, standard library only; `node` on the `PATH` adds the template-function checks, which are skipped without it; `BLUEDOC_BROWSER_TESTS=1` adds the page tests, which drive headless Chrome, found in its usual places or named by `BLUEDOC_CHROME`). Each test works on copies of `skills/bluedoc/examples/` in a temp folder with its own `BLUEDOC_HOME`, and the server tests run `serve.py run` on a free port, so nothing touches `~/.bluedoc` or a running server; the helpers send the temp home's key with every request that sends `X-Bluedoc`, as an unlocked page does. The nine suites are `test_golden_examples` (the examples build clean and match `docs/examples/*.html`; regenerate those with `build.py <example> -o docs/examples/<name>.html` after a template change), `test_security` (script-injection probes against `build.validate`, `build.build` and the template's `safeUrl`, `inline` and `diffNum`, JSON blocks that parse as served when a doc quotes `<!--`, a diff ref that must not run the repo's textconv command, design screens framed with `sandbox="allow-scripts"` only and served with the sandbox CSP; with the browser, an escape screen that tries the parent page, storage, the server, the network, top navigation, popups and forms, framed and on its own), `test_server_guards` (path traversal, Host, cross-site POST and `wait` header checks, 400 for a bad `Content-Length` or `wait` timeout, and the design screen route: only a board's artboards and revs, no `X-Frame-Options`, doc pages still unframable; a presentation's deck card; a `?key=` link that unlocks any number of times until its hour is up, and `GET /__bluedoc/key` only for the page's own fetch with the cookie), `test_state` (the `/__bluedoc/state` guards and limits, a PUT and GET round trip, the seed, an import that adds only missing keys, state and replies across a restart, approvals bound to the doc the page showed and to its content, carried through revs that only mark progress and not past any other change (`build.approval_carries` on the plan and a design's screens), and the one-time import of older reply files), `test_page_state` (a doc's URL that a wider folder keeps; with the browser, the page's outbox: two paths with one doc id, a write answered with 404, Approve after an unseen edit, an approval kept through a step marked done and lost to a step's text edit, a doc that quotes `<!--`, what Request changes counts beside annotations: a plan's item comment until sent and again once edited, and "Need more details" on a plan and a review, sent once and reset by a newer rev, and a review's findings sections: the [Merged][Checklist][Diff] bar (Merged by default, its pick across a reload, an older saved value, the one-time hint, sticky and visible while scrolling), Merged's order (whole change, then by file and line, then findings not tied to code) and full rows, a pick in Merged on the checklist and the diff and back, Show more lines, item and line keys that resolve in Merged, the code and card under an open finding in Checklist, a pin shared by all three views, and links that show the view they need; and a page whose browser lost its cookies saving with the key it kept in `localStorage`), `test_resolves` (a doc's `resolves` must be a list of short comment ids, `patch --resolves` rewrites it on a bump and appends with `--no-bump`, the history keeps each revision's list; and the screen route's declared, undeclared and missing framework files) and `test_website` (`new website` with and without `--url`, a non-loopback URL refused, the pages-only contract, breakpoints and viewport heights, source hints checked against `board.root`, sections and variants, the acme-site example and `patch` printing its pages' sections and source, the website home card;
