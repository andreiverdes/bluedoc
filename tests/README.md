# Tests

Run `python3 -m unittest discover -s tests` from the repo root (Python 3.9+, standard library only; `node` on the `PATH` adds the template-function checks, which are skipped without it; `BLUEDOC_BROWSER_TESTS=1` adds the page tests, which drive headless Chrome, found in its usual places or named by `BLUEDOC_CHROME`). Each test works on copies of `skills/bluedoc/examples/` in a temp folder with its own `BLUEDOC_HOME`, and the server tests run `serve.py run` on a free port, so nothing touches `~/.bluedoc` or a running server; the helpers send the temp home's key with every request that sends `X-Bluedoc`, as an unlocked page does. The six suites are `test_golden_examples` (the examples build clean and match `docs/examples/*.html`; regenerate those with `build.py <example> -o docs/examples/<name>.html` after a template change), `test_security` (script-injection probes against `build.validate`, `build.build` and the template's `safeUrl`, `inline` and `num`, JSON blocks that parse as served when a doc quotes `<!--`, and a diff ref that must not run the repo's textconv command), `test_server_guards` (path traversal, Host, cross-site POST and `wait` header checks, and 400 for a bad `Content-Length` or `wait` timeout), `test_state` (the `/__bluedoc/state` guards and limits, a PUT and GET round trip, the seed, an import that adds only missing keys, state and replies across a restart, approvals bound to the doc the page showed and to its content, and the one-time import of older reply files), `test_page_state` (a doc's URL that a wider folder keeps; with the browser, the page's outbox: two paths with one doc id, a write answered with 404, Approve after an unseen edit, and a doc that quotes `<!--`) and `test_key_roundtrip` (every key the annotator's `keyOf` emits on the examples resolves in `build.py patch`, and `SKILL.md` and `references/schema.md` list every key form).
